Planetary terrain flight#

Atlas needs a terrain system that can take a viewer from an interplanetary view down to a low altitude, follow the surface, and keep the best available measured terrain under the camera. “All known planetary bodies” is an open-ended catalog, so coverage must be data driven rather than a hard-coded list of planets. A body can appear in the catalog before a usable elevation model exists; the viewer must say so instead of inventing topography.

Terrain model contract#

Each body is a named, versioned terrain collection with:

  • A reference radius and coordinate reference system.

  • One or more global elevation sources, with resolution, vertical datum, coverage, no-data mask, citation, and license.

  • Zero or more local elevation sources, each with its footprint and finer resolution.

  • Optional imagery sources, explicitly separate from elevation.

  • A build record that links source IDs and processing version to generated tiles.

Terrain is streamed by camera location and level of detail. Global data provides continuous navigation; regional products replace it only inside their measured footprints. Tile seams, nodata, vertical datum changes, and source resolution are represented in the data, not hidden by synthetic detail. Rendering may exaggerate relief for legibility, but telemetry and source metadata remain in physical units.

The Mars collection now has two USGS controlled CTX stereo DTM layers with approximately 20 m post spacing and MOLA geoid heights: Melas Chasma in Valles Marineris and a Jezero-region model covering the dashboard’s Jezero target. Both source products are CC0. The 93-tile Melas layer remains intact; the Jezero model has 188 compact int16 tiles. A global USGS MGS MOLA DEM at 463 m posting is processed into 40,960 int16 tiles at levels 6–7, covering the full planet; the generated collection occupies about 2.2 GB and remains outside the APK at data/terrain/mars. Its manifest records the MOLA geoid source datum, nodata sentinel, scale, source URL, and 3,389.5 km renderer reference radius. The USGS/ESA HRSC–MOLA Blend Global DEM v2 (200 m/pixel source posting, 106,694 × 53,347 int16, −32768 nodata, IAU Mars 2000 sphere, 3,396.19 km radius) is being ingested from the 11.38 GB USGS archive. HRSC contributes about 44% of the globe; remaining areas are blended from coarser MOLA, so 200 m is the source grid spacing and not uniform effective resolution. The projector has only 2.7 GB free, so installing this pack requires replacing the older coarse MOLA tile set or using a managed external terrain pack. The USGS Mercury MESSENGER global DEM (665 m posting) has 8,192 int16 level-6 tiles, retaining its 2,439.4 km reference sphere and −180°…180° longitude frame. The DLR Dawn Ceres HAMO global DTM (136.7 m posting) has 8,192 int16 level-6 tiles with its 470 km reference sphere. Mercury and Ceres remain outside the APK at data/terrain/mercury and data/terrain/ceres (roughly 630 MB and 533 MB on disk).

For Mars extension, the USGS Analysis Ready Data STAC API exposes the mro_hirise_socet_dtms collection (typically 1–2 m posting) and mro_ctx_controlled_usgs_dtms (typically 20 m). A bbox query around Melas Chasma returned multiple overlapping DTMs in both collections. Prefer spatially targeted ingest near named destinations, and preserve each source projection and footprint during reprojection rather than assuming every product is a global equirectangular raster. See the HiRISE DTM collection and CTX DTM collection.

An additional 1.0137 m/pixel HiRISE controlled DTM, DTEEC_005533_1975_005388_1975_A01, covers Pangboche Crater on Olympus Mons at 17.2799°N, 133.3247°W. The USGS STAC record identifies University of Arizona production, CC0 license, 62.5% valid raster coverage, and the Mars 2015 ocentric equirectangular frame (3,396.19 km reference sphere). Its 25,207 × 8,449 source raster is tiled as an int16 layer with nodata preserved: 1,934 tiles through level 15 at data/terrain/mars/hirise-olympus-pangboche-dtm-1m-PSP_005533_1975. The Olympus destination now points inside this footprint, and its level-15 tile contains valid terrain (20,216–20,353 m in that tile; 20,308 m at the preset coordinate). Source: USGS STAC item.

Ceres now has seven local 32.04 m/pixel Dawn LAMO DTM layers—Ahuna Mons, Ernutet, Haulani, Ikapati, Kupalo, Occator, and Yalode—in addition to the global 136.7 m/pixel HAMO DTM. They contain 21,912 int16 tiles through levels 7–8 at data/terrain/ceres/dawn-lamo-<region>-dtm-32m. The existing Occator preset and six new named presets each resolve to a level-8 tile with 65,536 valid samples at the selected coordinate. Kupalo uses a local Lambert azimuthal source projection whose footprint crosses the 180° longitude seam; the builder now splits wrapped footprints for the geographic tile matrix, and the renderer recognizes wrapped coverage bounds. scripts/ingest_ceres_lamo_dtms.py downloads and validates the six non-Occator DLR products before tiling; it verifies their 470 km Ceres reference frame, 32.04 m posting, int16 type, and nodata metadata. The DLR page requests credit; no separate license is stated in the source metadata, so each manifest layer records that provenance without asserting a license. Sources: DLR Ceres DTM products and USGS Gazetteer of Planetary Nomenclature.

Build and runtime pipeline#

  1. Maintain a body/source registry. Harvest source metadata and footprints from authoritative catalogs; do not assume every cataloged object has terrain.

  2. Ingest source rasters without changing their provenance. Normalize horizontal coordinates to a body-fixed frame and vertical values to a declared body datum. Preserve original values and nodata masks.

  3. Build a global level-of-detail pyramid for each supported body, then add local high-resolution models as separate layers. Use an open, streamable terrain-tile format and retain per-tile source attribution.

  4. Render tiles around the camera with asynchronous requests, cache limits, and fallback to the next coarser covered level. Use imagery draped independently from elevation.

  5. Add flight controls: select a body, choose a named destination, set altitude/speed, and fly a path while respecting local terrain and reporting current data resolution.

  6. Automate completeness checks for gaps, overlaps, datum compatibility, source license, tile bounds, and maximum supported level. A body is only marked flyable when its generated data and viewer behavior have been verified.

Projector and mission path#

The projector renderer is an Android WebView using bundled Three.js WebGL, separate from the native starfield View. The parent dashboard sends mission commands to /api/terrain; the projector view reads mission state from the same local server. A mission replay can carry the camera from interplanetary space into a body-fixed atmospheric entry or orbital pass, with local terrain requested near the recorded path. The separate user-targeted direct approach remains useful for flying to a selected destination.

Recorded probe trajectories#

scripts/spice_trajectory_to_json.py converts a local SPICE meta-kernel and SPK coverage interval into the projector’s compact JSON replay format. It records ET (TDB seconds past J2000), body-fixed planetocentric latitude/east longitude (to match the terrain grids), altitude above the SPICE reference ellipsoid, spacecraft, frame, kernel source, URL, and citation. It requires spiceypy and a complete meta-kernel; it does not download kernels or guess kernel coverage.

The projector accepts schema version 1 at /trajectory-data/{id}/trajectory.json for body-fixed flight and schema version 2 for J2000 inertial Cartesian flight with an explicitly declared origin (Sun or Solar System barycenter). IDs are restricted to letters, digits, underscore, and hyphen. Samples are time ordered and retain frame, time scale, coverage, and source attribution. The native server serves trajectory files bundled under player/app/src/main/assets/trajectories/. Body-fixed playback requests nearby elevation tiles when the path is within terrain range.

The bundled mro-psp-jezero-2007-01-29 asset replays two hours of MRO reconstructed orbit over Jezero from 2007-01-29 at 10-second samples (722 points). Playback compresses this interval into four minutes after the 32-second space approach. It was exported with the converter from the coordinated PDS MRO SPICE archive using the reconstructed navigation SPK mro_psp2.bsp, Mars ephemeris mar063.bsp, planetary ephemeris de410.bsp, PCK pck00008.tpc, and LSK naif0008.tls. Its altitude range is approximately 252–315 km above the SPICE Mars reference ellipsoid. See the MRO PDS archive description and the archived reconstructed orbit SPK.

Phoenix is ingested in two coordinate-aware segments. phoenix-cruise-2007-08-04-to-2008-05-25 uses 14,187 samples from the NAIF phx_cruise.bsp, in Sun-centered J2000 coordinates, and includes contemporaneous planetary positions for the Three.js solar-system replay. Coverage starts at 2007-08-04 10:47:06 UTC, the first epoch with complete loaded-kernel support, and ends at 2008-05-25 23:30 UTC. phoenix-edl-2008-05-25 uses 453 one-second samples from the reconstructed phx_edl_rec_traj.bsp, transformed into Mars-fixed latitude/longitude and ellipsoid height, from 23:30:58 to 23:38:30 UTC. Its final sample is 2.639 km below the SPICE reference ellipsoid and is retained rather than clamped. Both use Phoenix archive frame/time kernels and planetary ephemerides. See the NAIF Phoenix SPK archive and its Phoenix kernel directory.

The native server exposes trajectories/catalog.json at /trajectory-data/catalog.json; the parent dashboard reads this catalog to populate the replay selector. It currently contains 26 records: the Apollo 11 S-IVB post-separation departure reconstruction, the Apollo 11 LM P-66 final-descent local profile, Phoenix cruise and EDL, the MRO Jezero pass, and 21 Sun-centered JPL Horizons mission histories for Voyager 1/2, Cassini, Galileo, New Horizons, Juno, Mars Reconnaissance Orbiter, Mars Odyssey, Mars Express, MAVEN, Curiosity, Perseverance, Dawn, Rosetta, MESSENGER, Parker Solar Probe, OSIRIS-REx, BepiColombo, NEAR Shoemaker, InSight, and Tianwen-1. Each record declares its own coverage and cadence. This is a curated initial set, not an exhaustive catalog of every flown probe. The S-IVB trajectory is the uncrewed launch stage, not the Apollo 11 command/service module or lunar module. The LM local profile is a digitized NASA reconstruction without lateral orientation and is not a geodetic terrain path. Mission-by-mission coverage must be established from each agency archive; files are not interpolated across missing SPK intervals or relabeled as reconstructed when they are planned trajectories. See trajectory coverage and ingest details.

Irregular bodies#

The catalog cannot assume every body is a sphere with a latitude/longitude DEM. USGS Astrogeology’s small-body inventory includes global elevation shape models for Ceres and Vesta, sub-meter global shape for Bennu, and meter-scale shape models for comet 67P. These products are often meshes or SPICE DSK files rather than map rasters. The long-term body record therefore needs a shape representation and coordinate frame per product; irregular-body terrain should render its measured facets directly instead of warping them onto a sphere. See the USGS small-body foundational data inventory for coverage and product formats.

scripts/build_terrain_tiles.py ingests a body-fixed elevation GeoTIFF, transforms it to the source CRS’s associated body longitude/latitude CRS, and writes separate per-source float32 tile layers plus a manifest. It supports global rasters whose longitudes use either −180°…180° or 0°…360° (including projected cylindrical grids centered at 180°). It refuses inputs without a body-fixed geographic CRS and requires the operator to name the vertical datum, citation, and license, so it cannot silently inherit Earth WGS84 or an assumed height reference. Example for the public-domain MOLA mosaic:

python3 scripts/build_terrain_tiles.py Mars_MGS_MOLA_DEM_mosaic_global_463m.tif data/terrain \
  --body Mars --layer-id mola-global-463m --layer-name 'MOLA global DEM 463 m' \
  --citation 'MOLA Team, Mars MGS MOLA DEM 463m, USGS Astrogeology' \
  --license CC0 --vertical-datum 'Mars areoid, GMM-2B' --max-level 7

The projector looks for an installed manifest at /terrain-data/<body>/manifest.json and loads the finest covering tile in its configured range. Tiles are gzip-compressed float32 or int16 grids, as declared in the manifest. The starter CTX collection is bundled at player/app/src/main/assets/terrain-data/mars; the Android server lets an external-files terrain-data collection override bundled data. Larger collections can stay outside the APK and be added with adb push data/terrain/<body> /sdcard/Android/data/institute.castalia.astrarium/files/terrain-data/<body> for Moon, Mercury, Venus, Earth, Mars, Ceres, Vesta, Pluto, Charon, or Titan.

Current state and next data work#

The projector has a bundled Three.js approach scene, regional 20 m CTX terrain for Melas Chasma and Jezero, an external 463 m global MOLA surface for Mars, a 2.03 m HiRISE DTM patch over Melas Chasma, and the 0.997 m HiRISE stereo DTM for Phoenix’s actual landing site. The Phoenix DTM, DTEPC_008591_2485_008644_2485_U01, is the USGS Astrogeology ARD/University of Arizona product centered at 68.20°N, 234.2°E. It is tiled at levels 10–16 as 8,404 int16 tiles in data/terrain/mars/hirise-phoenix-landing-site-dtm-1m-DTEPC_008591_2485_008644_2485_U01 and bundled under player/app/src/main/assets/terrain-data/mars; the level-16 tile at the reconstructed EDL endpoint contains 65,536 valid samples and reads −4,131 m. Of the 453 one-second EDL samples, 216 lie within the DTM bounds and 214 land on valid source pixels, so global MOLA supplies the broad approach when installed and the local DTM supplies the covered final segment. This DTM footprint is about 7.7 × 10.1 km, not a full track model. The Phoenix landing site is now a selectable destination. HiRISE DTMs are MOLA-controlled; posting is not the same as effective terrain resolution, and horizontal alignment and stereo artifacts vary. See the USGS HiRISE DTM archive and accuracy guidance, Melas Chasma DTM record, and Phoenix landing-site DTM record. The Vesta DTM is represented as radial elevation relative to a 262.7 km mean radius, converted from absolute radius values, and tiled at level 5 to match its 48 pixels/degree source sampling. It uses float32 because the full global relief exceeds the range of signed 16-bit meters. The source coordinate frame is the product’s Claudia 2013 shifted frame. The processed layer has 2,048 tiles and occupies about 327 MB at data/terrain/vesta; source details are in the USGS Vesta DTM record. The user-targeted path reaches Mars from space and can descend to the bundled Phoenix site patch or installed terrain patches; without installing the external MOLA collection, global Mars context is limited to regions covered by the bundled CTX DTMs. Global Mercury, Venus, and Ceres DEMs are staged at data/terrain/mercury, data/terrain/venus, and data/terrain/ceres; Pluto’s masked New Horizons DEM is tiled at data/terrain/pluto. These collections can be installed externally. Coverage across bodies and missions remains incomplete.

The Moon now has an external global foundation from NASA GSFC’s May 2024 LOLA principal-axes global shape model (64 pixels/degree, approximately 474 m at the equator; elevations in meters above the 1737.4 km radius). The processed layer has 8,192 level-6 int16 tiles and covers the globe. The raster is in MOON_PA_DE421, while map coordinates use the lunar mean-Earth frame; the projector rotates terrain normals with the NAIF moon_080317.tf DE421 PA-to-ME matrix (about 0.02885°, or 875 m on the surface). The higher-resolution USGS LOLA global DEM at 256 pixels/degree (118 m at the equator, public domain, ME/DE421 frame, source scaler 0.5 m/DN) is tiled at levels 7–8 with 163,840 int16 tiles (32,768 at z7 and 131,072 at z8) in data/terrain/moon/lola-global-dem-118m-2014. See the NASA PGDA 2024 global shape model and USGS LOLA 118 m DEM record.

The Moon also has regional SLDEM2015 coverage at the Apollo 11, 15, and 17 sites. The product combines LOLA control with Kaguya Terrain Camera stereo and has 512 pixels/degree (~59 m posting at the equator, with effective terrain resolution around 60–100 m). The 0–30°N, 0–45°E source tile is processed at levels 5–9 as 14,688 int16 tiles in data/terrain/moon/sldem2015-north-equatorial-60m-0-45e (about 778 MB compressed). The three site z9 tiles contain measured elevations: −1,929 m at Apollo 11, −1,927 m at Apollo 15, and −2,628 m at Apollo 17 relative to the 1,737.4 km lunar reference radius. These regional tiles use the ME/DE421 frame to align with the global LOLA model; the 512 ppd input is not global coverage. Sources: NASA GSFC SLDEM2015 product and SLDEM2015 regional tile archive.

NASA GSFC’s 5 m/pixel LOLA GeoTIFF mosaic from 87°S to the south pole has downloaded and verified at 3,465,285,714 bytes. The file is a 40,000 × 40,000 float32 raster in south-polar stereographic coordinates, with a 200 km square extent and MOON_ME/DE421 orientation. Its 5 m samples are elevation in meters. scripts/build_moon_south_pole_tiles.py converts a chosen local neighborhood to projected tiles rather than stretching the polar grid into longitude/latitude: the -89°, 0° south-pole destination now has 676 level-8 tiles over a 20 km square in data/terrain/moon/lola-south-pole-5m-87s (about 8.6 MB compressed). The Three.js terrain loader places these stereographic tiles directly on the lunar sphere. This is local high-resolution coverage, not global 5 m coverage. See the South Pole LOLA DEM Mosaic.

Earth now has NOAA’s ETOPO 2022 global surface relief model at 30 arc-seconds tiled at levels 5–7: 43,008 int16 tiles in data/terrain/earth/etopo2022-global-surface-relief-30s. This global relief includes land, ocean bathymetry, and ice surface, with heights referenced to the EGM2008 geoid. A local USGS 3DEP 1 m bare-earth DEM tile now covers the Grand Canyon South Rim preset. Its 10 km square UTM 12N tile is tiled at levels 12–16 (1,911 int16 tiles) in data/terrain/earth/usgs-3dep-grand-canyon-1m-x40y400-2019; the preset’s level-16 tile contains 65,536 valid samples (736–826 m). Elevations use NAVD88 with Geoid12B and the source horizontal CRS is NAD83(2011), UTM zone 12N. This is a local patch, not 1 m coverage of the full canyon or Earth. ETOPO remains the regional-scale fallback outside the patch. Sources: NOAA ETOPO 2022, USGS 3DEP tile metadata, and USGS DEM projection and datum guidance.

Venus now has the USGS Magellan global altimetry DEM at 4,641 m/pixel, tiled at levels 3–4 with 639 int16 tiles in data/terrain/venus/magellan-global-topography-4641m-v02. Heights are in meters relative to the 6,051 km Venus reference sphere; the product is public domain. The Maxwell Montes preset uses 65°N, 6°E and resolves to a valid level-4 tile. Source: USGS Venus Magellan Global Topography 4641 m.

Io is now selectable as a projector destination, using its 1,821.6 km mean radius, with a Loki Patera preset. The terrain catalog marks its DEM as identified but not installed: White et al. (2014) report a stereo-derived elevation model covering about 75% of Io, distributed as the 252.3 MB IoDEM.cub ISIS cube. The USGS inventory confirms the source and coverage, but the AGU/Wiley supplementary-file endpoint currently returns HTTP 403 from this environment, and the USGS listing provides no alternate DEM download. No terrain elevations are fabricated; Io currently renders as a smooth body until the cube can be acquired and converted. Separately, the USGS Galileo/Voyager global mosaic is imagery and must not be treated as elevation. Sources: USGS Jupiter and satellites inventory and White et al. 2014.

The USGS New Horizons Pluto global DEM (about 300 m posting) is tiled at levels 4–6: 5,181 int16 tiles in data/terrain/pluto/new-horizons-global-dem-300m-2017, retaining the raster’s nodata outside mapped terrain. Raster verification found 143,839,310 valid cells in a 24,888 × 12,444 raster, elevations from −4,101 to 6,491 m relative to the 1,188.3 km reference sphere. Its global rectangular extent is only an indexing extent; the actual New Horizons mapped coverage is about 42%. The projector offers Sputnik Planitia at 25°N, 175°W; its level-6 tile has measured values. The product record requests citation and does not state a license, which is recorded as such in the manifest. Charon’s about-300 m DEM is now tiled at levels 4–5 with 1,244 int16 tiles in data/terrain/charon/new-horizons-global-dem-300m-2017. The Vulcan Planum preset is at 2.8°S, 92.8°W; its level-5 tile contains 41,160 valid samples, while the measured coverage remains partial (about 40%). The Pluto and Charon product records are here and here.

Titan now has the Cassini RADAR GTDR interpolated global shape model, tiled at levels 3–4 with 640 int16 tiles in data/terrain/titan/cassini-gtdr-interpolated-global-8ppd-2013. The source package contains the globally gridded GTIED model at 8 pixels/degree (~5.6 km per pixel at the equator), assembled from two PDS-labeled hemisphere rasters. Elevations range from about −1,659 to +468 m relative to the 2,575 km reference sphere. scripts/ingest_titan_gtdr.py repeats the assembly from the published ZIP package. The terrain collection uses the GTDR’s spline-interpolated model, a continuous model of sparse RADAR altimetry/SARTopo observations rather than uniformly measured 5.6 km detail. The Huygens landing-site preset uses 10.3°S, 167.7°E, corresponding to NASA’s 192.3°W coordinate; its z4 tile contains valid values. See the USGS GTDR product and Cassini GTDR package mirror.

Next, finish the HRSC–MOLA tile build and prepare an installable Mars terrain pack sized for the projector. Then continue regional elevation ingestion for Ceres and Mars, add available terrain sources for other mapped bodies, and expand the recorded probe catalog beyond the 26 current entries. Add trajectory coverage only with explicit frame, time interval, and reconstruction/plan provenance. The Phoenix cruise playback uses scaled solar-system distances to make a roughly 1.5 AU transfer leg visible in the same Three.js scene; body sizes and replay time are visual scales, not to-scale travel time.

Completion criteria#

The objective is not complete when a globe merely looks textured. It is complete when the catalog covers the chosen authoritative set of known planetary bodies; every body has an honest availability state; bodies with data can be flown over with their best processed terrain coverage; and each displayed level can be traced to its source, resolution, and datum. Bodies without elevation data must remain discoverable and clearly marked as unavailable for terrain flight until source data becomes available.
